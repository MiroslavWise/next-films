Функциональность серверной части:

Создай API:

GET /api/games/movie-choice/round
- Проверяет Telegram initData из заголовка x-telegram-init-data.
- Валидирует пользователя.
- Применяет rate limit.
- Возвращает до 3 случайных фильмов, за которые пользователь ещё не голосовал.
- Если доступных фильмов нет, возвращает пустой список и флаг finished: true.

POST /api/games/movie-choice/vote
- Проверяет Telegram initData.
- Применяет rate limit.
- Валидирует тело запроса через Zod.
- Тело запроса содержит массив выбора пользователя.
- Минимальная длина массива: 1.
- Максимальная длина массива: 3.
- Каждый элемент содержит movieId и choice.
- choice должен быть одним из: WATCH_MANY, WATCH_ONCE, REMOVE.
- movieId не должны повторяться внутри одного запроса.
- Сервер должен использовать транзакцию.
- Для каждого фильма:
  - если пользователь ещё не голосовал, создаётся Vote и увеличивается нужный счётчик;
  - если пользователь уже голосовал за этот фильм, счётчик не увеличивается, голос можно пропустить или пометить как skipped.
- После обработки сервер возвращает следующий раунд: до 3 случайных фильмов, за которые пользователь ещё не голосовал.
- Если фильмов не осталось, возвращает finished: true.

Валидация Telegram initData на сервере:

Создай функцию валидации, например:
src/lib/telegram/validate.ts

Она должна:
1. Брать строку initData из заголовка.
2. Парсить параметры как query string.
3. Исключить поле hash.
4. Отсортировать оставшиеся пары ключ-значение по алфавиту.
5. Собрать data_check_string.
6. Проверить подпись с использованием BOT_TOKEN.
7. Использовать алгоритм из документации Telegram WebApp:
   secret_key = HMAC_SHA256("WebAppData", BOT_TOKEN)
   hash = HMAC_SHA256(data_check_string, secret_key)
8. Сравнить hash безопасно, через crypto.timingSafeEqual или аналог.
9. Проверить, что auth_date не старше 24 часов.
10. Распарсить поле user и вернуть объект пользователя.
11. Если проверка не прошла, вернуть ошибку.

В production BOT_TOKEN должен быть только на сервере.
Нельзя использовать NEXT_PUBLIC_BOT_TOKEN.

## Важные моменты, которые я заложил в промпт

### 1. Не просто счётчики, а защита от накрутки

Ты описал, что результаты должны писаться в БД как три счётчика. Это нормально для MVP. Но если не хранить сам факт голоса, пользователь сможет бесконечно отправлять запросы и накручивать счётчики.

Поэтому в промпт добавлена таблица `Vote`:

- один пользователь — один голос за один фильм;
- повторный голос не увеличивает счётчик;
- можно видеть, какие фильмы пользователь уже оценил;
- можно показывать пользователю только неоценённые фильмы.

Это всё ещё сохраняет твою идею с тремя `int`-счётчиками в таблице фильма.

---

### 2. Лучше отправлять голосование одним батчем

Вместо 3 отдельных запросов на каждый фильм:

```text
1 запрос на загрузку 3 фильмов
1 запрос на отправку выбора за 3 фильма
```

Это важно для:

- Vercel limits;
- Telegram Mini App UX;
- меньшего числа serverless-вызовов;
- меньшего риска упереться в rate limit;
- более быстрой работы.

---

### 3. Для Telegram нужна проверка `initData`

Если просто полагаться на данные с клиента, любой человек сможет подделать запросы через curl или DevTools.

Поэтому в промпт включена серверная проверка `Telegram.WebApp.initData` через `BOT_TOKEN`.

Важно:

- `BOT_TOKEN` нельзя делать `NEXT_PUBLIC_...`;
- он должен быть только в серверных переменных окружения;
- проверка должна происходить в API-роутах.

---

### 4. Для Vercel и PostgreSQL нужен pooler

Если использовать обычное прямое подключение к PostgreSQL из serverless-функций, можно быстро упереться в лимит соединений.

Особенно это актуально для:

- Neon;
- Supabase;
- Vercel Postgres;
- Railway;
- Render.

В промпт заложено:

- использовать `DATABASE_URL` для runtime;
- использовать `DIRECT_URL` для миграций;
- применять pooled connection, если БД это поддерживает.

---

### 5. Rate limit лучше делать через Upstash

Сам по себе Next.js API route не даёт удобного распределённого rate limiter. In-memory limiter будет работать плохо, потому что функции на Vercel могут быть разными инстансами.

Хороший вариант:

- Upstash Redis;
- `@upstash/ratelimit`;
- лимиты по `telegramUserId`;
- fallback по IP, если пользователь не распознан.

## Идеи: что можно прокачать в приложении

Ниже — идеи, которые можно добавлять после MVP.

## Продуктовые улучшения

### 1. Ежедневный вызов

Сделать режим:

> «3 фильма дня»

Пользователь заходит раз в день и получает новую подборку. Это повышает возврат.

Можно добавить:

- стрики;
- награды за серию дней;
- счётчик дней.

---

### 2. Личный профиль

Показывать пользователю:

- сколько фильмов он оценил;
- сколько фильмов «убрал из киноиндустрии»;
- сколько фильмов оставил в любимых;
- его топ решений.

Например:

- «Вы посмотрели бы снова: 42 фильма»;
- «Хватит одного: 18 фильмов»;
- «Убрать из киноиндустрии: 7 фильмов».

---

### 3. Результаты и статистика

После голосования можно показывать:

- как проголосовали другие;
- процент по каждому фильму;
- общее число голосов;
- рейтинг фильма по решениям.

Например:

- 65% хотят смотреть много раз;
- 25% хватит одного;
- 10% убрать.

Это сильно повышает вовлечение.

---

### 4. Шеринг результата

Сделать кнопку:

> «Поделиться результатом»

Можно генерировать картинку:

- постер фильма;
- решение пользователя;
- название приложения;
- ссылка на Mini App.

Это даёт виральность.

---

### 5. Сравнение с друзьями

Если пользователь оценивает фильм, можно показать:

- как проголосовали его друзья;
- совпал ли выбор;
- процент совпадений.

Для этого понадобится:

- таблица друзей;
- инвайты через Telegram;
- или хотя бы публичные профили.

---

### 6. Достижения

Например:

- «Критик» — 10 фильмов «убрать из киноиндустрии»;
- «Фанат» — 20 фильмов «смотреть много раз»;
- «Гурман» — оценить 50 фильмов;
- «Киноклуб» — пригласить друга;
- «Ежедневный зритель» — заходить 7 дней подряд.

---

### 7. Жанровые подборки

Не просто случайные фильмы, а категории:

- комедии;
- триллеры;
- хорроры;
- драмы;
- фантастика;
- аниме;
- сериалы позже;
- фильмы по десятилетиям.

Это сделает приложение более глубоким.

---

### 8. Карточка фильма

Сейчас можно показывать только постер. Но позже стоит добавить детальную страницу:

- название;
- жанры;
- актёры;
- режиссёр;
- продюсер;
- описание;
- рейтинг;
- постер;
- кадры;
- похожие фильмы.

Но для MVP это не обязательно.

---

### 9. Режим «один фильм»

Кроме игры на 3 фильма можно сделать быстрый режим:

- показывается один фильм;
- пользователь быстро голосует;
- сразу показывается следующий.

Это может быть даже динамичнее.

---

### 10. Топы и рейтинги

На основе голосов можно строить:

- топ фильмов, которые хотят смотреть много раз;
- фильмы, которым «хватит одного»;
- фильмы, которые чаще всего «убирают из киноиндустрии»;
- самые спорные фильмы;
- самые переоценённые фильмы;
- скрытые жемчужины.

## Технические улучшения

### 3. Нормализация базы

Сейчас в промпте жанры и актёры могут быть массивами строк:

Но позже лучше сделать отдельные таблицы:

- Actor;
- Director;
- Producer;
- MovieGenre;
- MovieActor.

Это даст:

- фильтры;
- поиск;
- страницы актёров;
- страницы режиссёров;
- рекомендации.

### 4. Кэширование

Можно кэшировать:

- главную страницу;
- список игр;

Для этого подойдут:

- Next.js cache;
- Redis;
- Upstash;

### 5. Аналитика

Добавить события:

- открыл приложение;
- начал игру;
- завершил раунд;
- нажал кнопку;
- получил ошибку;

Можно использовать:
